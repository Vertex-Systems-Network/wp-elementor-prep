# P16 R0 — Gutenberg / WordPress Block Foundation Snapshot

Date: 2026-09-14  
Roadmap: #119  
Implementation issue: #341

## Purpose

Retain the official-platform facts used to start the first bounded P16 Gutenberg foundation. This snapshot supports a repository-owned normalized parsed-block review contract and a read-only documented-core capability registry. It does **not** authorize raw block markup generation, target compatibility, editor validity, rendering parity, WordPress import, production acceptance or download.

## Official platform findings

### 1. Saved block content is comment-delimited markup

WordPress documents block storage as HTML-based syntax distinguished by HTML comments. Core block delimiters use the `wp:` prefix and omit the `core` namespace in the saved comment form. Block settings/attributes may be stored as a JSON object inside the delimiter.

Official reference:
https://developer.wordpress.org/block-editor/getting-started/fundamentals/markup-representation-block/

This means a future native serializer must follow WordPress's documented block grammar rather than inventing a private clipboard or alternate markup format. This P16 slice does not implement that serializer.

### 2. `parse_blocks()` returns a recursive parsed-block tree

WordPress documents `parse_blocks( string $content )` as parsing post content into a tree. The documented parsed block shape includes:

- `blockName: string|null`;
- `attrs: array`;
- `innerBlocks: array[]`;
- `innerHTML: string`;
- `innerContent: array`.

Top-level non-block content is documented as appearing as a block with no `blockName`.

Official reference:
https://developer.wordpress.org/reference/functions/parse_blocks/

The repository contract introduced by #341 is intentionally a **normalized subset** containing only `blockName`, `attrs`, `innerBlocks`, and `innerHTML`. It is not represented as the raw `parse_blocks()` return type because WordPress also exposes `innerContent` and may evolve parser behavior independently.

### 3. WordPress owns parsed-block serialization semantics

WordPress provides `serialize_block()` / `serialize_blocks()` for converting parsed block structures to saved post-content markup.

Official references:
https://developer.wordpress.org/reference/functions/serialize_block/
https://developer.wordpress.org/reference/functions/serialize_blocks/

The normalized repository serializer in this foundation emits JSON for the repository-owned review envelope only. It does **not** call or emulate WordPress's block serializer, and therefore cannot be used as proof of a WordPress round trip.

### 4. Current documented Block API version is 3

The current Block Editor Handbook documents:

- Version 3 for WordPress 6.3 and later;
- iframe-related behavior introduced/evolved across later WordPress releases.

Official reference:
https://developer.wordpress.org/block-editor/reference-guides/block-api/block-api-versions/

API version 3 is retained only as documentation evidence for exact block types in the first capability registry. It is not a compatibility claim for an arbitrary target WordPress installation.

### 5. First exact documented-core registry

Current official block reference pages identify the following exact names and API Version 3:

- `core/paragraph`
  https://developer.wordpress.org/block-editor/reference-guides/core-blocks/core-blocks-text/core-block-paragraph/
- `core/heading`
  https://developer.wordpress.org/block-editor/reference-guides/core-blocks/core-blocks-text/core-block-heading/
- `core/image`
  https://developer.wordpress.org/block-editor/reference-guides/core-blocks/core-blocks-media/core-block-image/
- `core/group`
  https://developer.wordpress.org/block-editor/reference-guides/core-blocks/core-blocks-design/core-block-group/

Only these four exact IDs are classified `DOCUMENTED_CORE` in the initial registry. Custom/unregistered names and top-level freeform content remain `REVIEW_REQUIRED`.

`DOCUMENTED_CORE` means the exact identifier + API version are directly evidenced in current official documentation. It does not mean:

- the block is registered on a target site;
- the target WordPress/editor version accepts generated markup;
- the current attributes are valid for that target;
- the block can be generated by WP Builders Prepare;
- rendering/import/round-trip validation has passed.

### 6. Patterns are a separate target artifact surface

WordPress documents two supported pattern registration paths:

- theme `/patterns` files with a valid pattern header;
- `register_block_pattern()`.

Official references:
https://developer.wordpress.org/themes/patterns/registering-patterns/
https://developer.wordpress.org/reference/functions/register_block_pattern/

Pattern/theme/plugin packaging is outside #341. A later P16 slice must define a separate versioned package contract before any native pattern artifact is claimed.

## Repository contract decisions for #341

### Normalized parsed-block envelope

Version:

`gutenberg-normalized-parsed-block-v1`

Envelope:

- `schemaVersion: 1`;
- `contractVersion`;
- `blocks` array.

Normalized node:

- `blockName: string | null`;
- `attrs: plain JSON object`;
- `innerBlocks: normalized block[]`;
- `innerHTML: string`.

The contract deliberately rejects extra raw-parser fields such as `innerContent` so callers cannot confuse this repository model with WordPress's complete parsed structure.

### Conservative validation bounds

The first contract is fail-closed and bounded:

- maximum 10,000 normalized block nodes;
- maximum block nesting depth 64;
- conservative lowercase `namespace/name` identifiers for named blocks;
- `blockName=null` accepted only for top-level/freeform content;
- JSON-compatible attribute values only;
- bounded attribute key/string/depth/value counts;
- bounded `innerHTML` length;
- explicit diagnostic issue codes.

These limits are repository safety constraints, not WordPress platform limits.

### Capability-report authority boundary

The first P16 capability report is read-only evidence only. It always keeps:

- `targetCompatibilityClaim=false`;
- `productionAcceptance=false`;
- `generationEnabled=false`;
- `downloadEnabled=false`.

Freeform/custom/unregistered blocks are `REVIEW_REQUIRED` rather than inferred compatible or unsupported.

## Explicit non-scope for this foundation

This slice does not introduce:

- raw Gutenberg comment-delimited markup generation;
- `@wordpress/blocks` runtime execution;
- PHP `parse_blocks()` / `serialize_blocks()` execution;
- WordPress REST/site connection;
- live editor/import/render validation;
- dynamic block server-render proof;
- theme/plugin/pattern ZIP generation;
- Figma-to-Gutenberg semantic mapping;
- selected-section transfer;
- target-ready download authority;
- any production compatibility or acceptance claim.

## Next evidence needed before stronger P16 claims

Future slices must separately prove, as applicable:

1. documented native serialization behavior using a version-pinned WordPress/Gutenberg runtime;
2. exact target profile/version binding;
3. editor/import validation on a real supported target;
4. static vs dynamic block behavior;
5. asset/media handling;
6. pattern/package structure if that artifact class is offered;
7. Figma semantic mapping confidence and REVIEW fallbacks;
8. round-trip visual/structural QA before production acceptance.

Until those gates exist, the P16 foundation is a normalized offline review/capability layer only.
